# D1 無料枠優先の設計方針（kakebo_jp）

このPWAは少人数による個人利用を前提とし、D1の読み取り行数・書き込み行数・ストレージをできる限り抑えます。「SQLの呼び出し数が少ない」だけでは低コストとは限りません。各クエリの `meta.rows_read` / `meta.rows_written` が判断基準です。

公式資料: https://developers.cloudflare.com/d1/platform/pricing/

## 機能開発時の原則

1. **計算はブラウザ優先**: 日付表示、日本の祝日、カレンダーやフィルタ、OCR文字整形、すでに取得した明細の集計は端末側で計算する。ただし残高・記帳の正本と端末間同期は D1 を保つ。
2. **読む範囲を限定**: 明細は月・年・カーソルなど必要な範囲だけ読み、無条件の全表取得を避ける。日付検索は既存 `idx_entries_date` を使える `date >= ? AND date < ?` を使い、`substr(date,1,7)=?` を禁止する。
3. **同じ要求で重複読込しない**: 画面内の計算・複数コンポーネントは受信済みスナップショットを再利用。画面切替・スクロールのたびにログインや全テーブルを読み直さない。更新後・ログイン変更・別端末からの再同期・手動更新ではキャッシュを失効。
4. **書き込みは変化があるときだけ**: NAV は価格日と出所を確認して同値の書き込みを回避。固定費は同じ予定の二重登録を防ぎ、SBI移動は一度反映した行を再更新しない。自動記帳を端末のページ入場で実行しない。
5. **Cron を安易に増やさない**: 日本の非取引日の基金取得をスキップし、無効Cronや対象外の処理でD1を触らない。固定費の必要な補償ジョブは削除せず正確な記帳を優先。
6. **索引の乱造を避ける**: 索引は読み取りを減らせる一方、書き込み行数とストレージを増やす。新規索引は Preview / メモリ SQLite で `EXPLAIN QUERY PLAN` を確認してから採用する。既存 `idx_entries_date` および適用済み `idx_entries_sbi_due_unapplied` を優先。
7. **追加の有料サービスを前提にしない**: KVや有料のAnalyticsへの移行は自動的には行わない。そもそものデータ取得を少なくする方法が先。
8. **正確性と認証は削らない**: 財務APIの認証・衝突確認、同時更新の排他・再試行時の冪等性、バックアップ整合性を維持する。必要な読み取りを削って二重計上を起こさない。

## PR の受け入れ条件

- `npm run build` の全回帰テストが成功。
- 月次検索・固定費候補のような日付条件は索引で検索できることを `EXPLAIN QUERY PLAN` で確認。
- 新規の自動D1アクセス、Cron、SELECT全表走査、複数箇所の同一データ取得の有無を確認。
- D1の計測は **Cloudflare Analytics と既存実行ログを優先**。デバッグ目的で本番全表 SELECT を繰り返さない。
- サーバー側の保存・復元・同期は、データ欠落、重複、キャッシュの古い表示を防ぐ回帰テストを追加。

`functions/api/recurring-collision.js`、`functions/api/recurring-auto.js`、`functions/api/[[path]].js` の月次重複判定を `substr(date,1,7)` から索引利用可能な日付範囲へ変更。新しい D1 表・索引・定期ジョブは不要。
